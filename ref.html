TSU Dashboard IIS, CAC, and SQL Checklist

Use this page while deploying the dashboard to the work IIS server. It separates browser authentication, app authorization, and SQL permissions so setup issues can be traced to the right layer.

Deployment Goal

The target workplace setup uses IIS to identify the user and the application pool identity to reach SQL Server.

Authentication Model IIS authenticates the user with Windows/CAC authentication. The app reads that identity from IIS.
SQL Identity identity impersonate="false" keeps SQL access on the IIS app pool identity.
Main Expected Edit Change TSUDashboardDb to point at the work SQL Server and database.

Known local diagnosis: the earlier non-JSON error happened because IIS was not executing .ashx handlers. On work IIS, ASP.NET 4.x and handler mappings must be installed and enabled.

Required IIS Checks

These checks determine whether requests reach the dashboard code with the expected identity.

  • Confirm the site or application is running under an application pool using .NET CLR v4.0 and Integrated pipeline.
  • Confirm ASP.NET 4.x is installed and .ashx files are mapped to ASP.NET, not served by StaticFile.
  • Enable Windows Authentication for the authenticated dashboard.
  • Disable Anonymous Authentication for the authenticated dashboard paths.
  • Grant the application pool identity read/execute access to the deployed site folder.
  • Grant the application pool identity the required SQL permissions on TSU-Dashboard.

web.config Changes

Keep the authenticated dashboard protected, but do not block authenticated users at the IIS authorization layer.

Current work file reviewed:

C:\Users\micha\Downloads\TSU\TSU-Dashboard\TSU-Dashboard\web.config

1. Change Main Dashboard SQL Connection

Replace the local dashboard connection with the work SQL Server target.

<add name="TSUDashboardDb"
     connectionString="Data Source=WORK-SQL-SERVER;Initial Catalog=TSU-Dashboard;Integrated Security=True;TrustServerCertificate=True"
     providerName="System.Data.SqlClient" />

2. Keep App Pool SQL Identity

Keep this setting:

<identity impersonate="false" />

This makes SQL Server see the IIS app pool identity, while the app still reads the authenticated user from IIS.

3. Fix IIS URL Authorization Rule

Change needed: the current work config has an IIS URL Authorization rule for anonymous users only. For the authenticated dashboard, remove it or change it to all users.

Current risky rule:

<system.webServer>
  <security>
    <authorization>
      <add accessType="Allow" users="?" />
    </authorization>
  </security>
</system.webServer>

Use this instead if the rule is needed:

<authorization>
  <add accessType="Allow" users="*" />
</authorization>

4. Keep ASP.NET Authorization For The Authenticated App

This is correct for the main dashboard:

<authorization>
  <deny users="?" />
</authorization>

It prevents the app from running without a Windows/CAC identity.

Public Board Decision

The public board can be CAC-free only if IIS allows anonymous requests for the page and its data endpoints.

Public Paths

  • public-board-v2.html
  • js/public-board-v2.js
  • css/public-board-v2.css
  • api/public-board/socket.ashx
  • api/public-board/active-posts.ashx

Protected Paths

  • index.html
  • section-dashboard.html
  • section-command.html
  • user-admin.html
  • assignments-board/

If the public board must be viewable without CAC, work IIS must allow Anonymous Authentication for the public board paths. If work IIS disables Anonymous globally with no path-level override, the public board will also require CAC.

The public data endpoint still uses SQL, so the app pool identity needs read access to the dashboard database even for anonymous public-board viewing.

Layer separation: SQL Server access is separate from the CAC prompt. The browser is challenged by IIS. SQL is reached later by the server using the IIS app pool identity because identity impersonate="false" is set.

Database Checks

The dashboard can authenticate correctly and still fail if the work database is missing expected tables or defaults.

  • Run the numbered scripts in database\ in order for a new database.
  • For an existing database, run database\010_add_user_access_flags.sql before testing first-time login.
  • Run database\011_add_section_enabled.sql before deploying the section availability changes.
  • Confirm dbo.Users.CanAccessAssignmentsBoard and dbo.Users.IsTsuiAdmin both exist and have DEFAULT 0.
  • Bootstrap the first admin account with the exact identity returned by /api/auth/whoami.ashx.

Assignments Board Tables

Schema check: if the assignments board is part of the work deployment, the database also needs these tables:

  • dbo.ProjectBoardState
  • dbo.ProjectAssignments
  • dbo.ProjectWorkers
  • dbo.ProjectNotes

The scripts for some of these currently live under docs\sql\sql\SQLQuery3.sql, SQLQuery4.sql, and SQLQuery5.sql, not the main database\ folder. Confirm the work database already has them or add them to the deployment script set.

RUMP Checks

RUMP is a separate source database. Its failures should not be confused with IIS authentication failures.

  • Confirm RumpDb points to the correct work RUMP SQL Server.
  • Grant the IIS app pool identity read access to [RUMP].[dbo].[Projects] if RUMP prefill is needed.
  • Configure RumpPullQuery before using the RUMP pull feature. It must return Title and Description, with optional PointOfContact, LatestUpdate, and EstimatedCompletionDate.

One RUMP diagnostic handler currently returns detailed SQL/app-pool error text. Useful during setup, but not ideal for production users.

Production Hardening

Use detailed errors during setup only, then move to safer production settings.

  • Change customErrors mode="Off" after setup testing is complete.
  • Change httpErrors errorMode="Detailed" after setup testing is complete.
  • Avoid showing raw SQL exception text to normal users once the deployment is verified.
  • Confirm HTTPS is used because httpCookies requireSSL="true" is enabled.

Expected First-Run Flow

This is the normal path once IIS, SQL, and the database schema are aligned.

  1. User opens index.html.
  2. Browser calls api/auth/route.ashx.
  3. IIS supplies the Windows/CAC identity.
  4. The app creates or updates the matching row in dbo.Users.
  5. If the user is not active or has no section, the app routes to access-pending.html.
  6. After the exact user row is activated and assigned, the app routes to the correct dashboard page.
